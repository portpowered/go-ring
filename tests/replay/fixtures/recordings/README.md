# Sanitized recordings

`http/` contains one representative captured exchange for device listing and detail, device settings reads/updates, siren on/off, history devices and timelines, locations, groups, recording favorite/delete, device reboot, and the Duos live-view update. Additional request-body, status, or response-shape cases are in `http/variants/`; names of the original fixtures are stable. Request paths use placeholders for device, recording, and location identifiers while keeping literal route version segments. Query pairs are retained with sensitive values scrubbed. HTTP fixture bodies use structured JSON values and preserve the JSON-body flag, including the difference between an empty response and JSON `null`.

The captured ticket route is an observed HTTP endpoint on `prd-api-us.prd.rings.solutions`. Its relationship to the `api.prod.signalling.ring.devices.a2z.com` WebSocket is unknown; the fixture does not claim this route is the RTC connection's bootstrap counterpart.

`sessions/flow-21.json` and `sessions/flow-402.json` preserve the complete captured application-message order and direction from the two PTZ conversations. Protocol methods and enum values remain intact, including the device `supported_rpc_commands` arrays. Account, device, route, dialog, session, and command identities are replaced by semantic identity domain; adjacent `id` and `device_id` fields in one device object share a replacement. Numeric identifiers stay numeric and string identifiers stay strings. Dates, timezone names, SDP ICE credentials, fingerprints, and network addresses are synthetic; SDP lines and message order remain intact.

The JSON schemas are in `schemas/`, with a small regression schema for `null`, arrays, and identity value types. Create a local Python environment and install `tools/capture/requirements.txt` to run the extractor and tests. Rebuild the files from a private local mitmproxy dump with `python tools/capture/extract.py <capture-file>`; the source recording is not included.
